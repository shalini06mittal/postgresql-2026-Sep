## 1. Numeric Types

### 1.1 Overview

| Type | Storage | Range / Precision | Exact? |
|---|---|---|---|
| `smallint` (`int2`) | 2 bytes | -32,768 to 32,767 | Yes |
| `integer` (`int`, `int4`) | 4 bytes | -2,147,483,648 to 2,147,483,647 | Yes |
| `bigint` (`int8`) | 8 bytes | about ±9.22 x 10^18 | Yes |
| `numeric(p,s)` / `decimal(p,s)` | variable | Up to 131,072 digits before the decimal point; 16,383 after | Yes |
| `real` (`float4`) | 4 bytes | ~6 decimal digits precision | No |
| `double precision` (`float8`) | 8 bytes | ~15 decimal digits precision | No |
| `smallserial` / `serial` / `bigserial` | 2 / 4 / 8 bytes | Auto-increment shorthand (legacy) | Yes |
| `money` | 8 bytes | Currency amount, locale-dependent | Yes (fixed scale) |

**Rule of thumb:** Use `integer`/`bigint` for counts and IDs, `numeric` for money and anything requiring exactness, and `double precision` for scientific measurements where tiny rounding error is acceptable.

### 1.2 Integer Types

```sql
CREATE TABLE inventory (
    id       integer,
    qty      smallint,
    views    bigint
);

SELECT 2147483647::int;           -- OK
SELECT 2147483648::int;           -- ERROR: integer out of range
SELECT 2147483648::bigint;        -- OK
```

- Arithmetic that overflows raises an **error**. It does not silently wrap.
- `bigint` is a safe default for primary keys on tables that may grow large.

### 1.3 Auto-Incrementing Columns

**Recommended: identity columns** (SQL standard, PostgreSQL 10+)

```sql
-- If you try to provide the ID yourself:
-- PostgreSQL rejects it.

CREATE TABLE customers (
    id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL
);

-- BY DEFAULT allows explicit values; ALWAYS rejects them unless overridden
CREATE TABLE orders (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
);

INSERT INTO customers (name) VALUES ('Alice');
INSERT INTO customers (id, name) OVERRIDING SYSTEM VALUE VALUES (100, 'Bob');
```

**Legacy: serial**

```sql
CREATE TABLE legacy (id serial PRIMARY KEY);
-- Expands to: integer + a sequence + DEFAULT nextval(...)
```

**Sequences**

```sql
CREATE SEQUENCE invoice_seq START 1000 INCREMENT 1;
SELECT nextval('invoice_seq');
SELECT currval('invoice_seq');
SELECT setval('invoice_seq', 5000);
```

> Sequences are **not transactional**. Rolled-back inserts leave gaps. Never rely on gap-free IDs.

### 1.4 Arbitrary Precision: numeric

Syntax: `numeric(precision, scale)`

- **precision**: total significant digits
- **scale**: digits after the decimal point

```sql
CREATE TABLE prices (
    item  text,
    price numeric(10,2)     -- up to 99,999,999.99
);

INSERT INTO prices VALUES ('pen', 1.5);        -- stored as 1.50
INSERT INTO prices VALUES ('car', 1.999);      -- rounded to 2.00
INSERT INTO prices VALUES ('yacht', 1e10);     -- ERROR: numeric field overflow
```

| Declaration | Meaning |
|---|---|
| `numeric` | Unconstrained; stores any value exactly (up to the limits) |
| `numeric(p)` | Scale 0 (integer values) |
| `numeric(p,s)` | Fixed precision and scale |

- Values are **rounded** to the declared scale on insert.
- PostgreSQL 15+ allows a **negative scale** (round to tens, hundreds) and a scale larger than precision.
- Special values: `NaN`, and (PostgreSQL 14+) `Infinity`, `-Infinity`.
- `numeric` is slower than integer or float arithmetic, but correct for financial data.

```sql
SELECT 0.1::numeric + 0.2::numeric;      -- 0.3 (exact)
SELECT 10.00::numeric(6,2) / 3;          -- 3.3333333333333333
```

### 1.5 Floating Point Types

`real` and `double precision` follow IEEE 754 and store **approximate** values.

```sql
SELECT 0.1::float8 + 0.2::float8;            -- 0.30000000000000004
SELECT (0.1::float8 + 0.2::float8) = 0.3;    -- false
SELECT 0.1::numeric + 0.2::numeric = 0.3;    -- true
```

Special values: `'NaN'`, `'Infinity'`, `'-Infinity'`.

```sql
SELECT 'Infinity'::float8 > 1e308;    -- true
SELECT 'NaN'::float8 = 'NaN'::float8; -- true in PostgreSQL (unlike IEEE)
```

> **Never** use floats for currency. Never compare floats with `=` when values come from calculations.

### 1.6 Operators and Functions

**Operators**

| Operator | Description | Example | Result |
|---|---|---|---|
| `+ - *` | Add, subtract, multiply | `5 * 3` | `15` |
| `/` | Divide (integer division for ints) | `7 / 2` | `3` |
| `%` | Modulo | `7 % 2` | `1` |
| `^` | Exponent | `2 ^ 10` | `1024` |
| `\|/` | Square root | `\|/ 16` | `4` |
| `@` | Absolute value | `@ -5` | `5` |
| `&`, `\|`, `#`, `~`, `<<`, `>>` | Bitwise operations (integers) | `5 & 3` | `1` |

**Common functions**

| Function | Description | Example |
|---|---|---|
| `abs(x)` | Absolute value | `abs(-4.2)` gives `4.2` |
| `round(x)` / `round(x, n)` | Round | `round(3.14159, 2)` gives `3.14` |
| `ceil(x)` / `ceiling(x)` | Round up | `ceil(4.1)` gives `5` |
| `floor(x)` | Round down | `floor(4.9)` gives `4` |
| `trunc(x, n)` | Truncate | `trunc(4.987, 1)` gives `4.9` |
| `mod(a, b)` | Remainder | `mod(10, 3)` gives `1` |
| `div(a, b)` | Integer quotient | `div(10, 3)` gives `3` |
| `power(a, b)` | Exponent | `power(2, 8)` gives `256` |
| `sqrt(x)` | Square root | `sqrt(81)` gives `9` |
| `sign(x)` | -1, 0, or 1 | `sign(-9)` gives `-1` |
| `greatest(...)` / `least(...)` | Max / min of a list | `greatest(1, 5, 3)` gives `5` |
| `random()` | Random value in [0, 1) | `random()` |
| `generate_series(a, b, step)` | Set of numbers | `generate_series(1, 5)` |
| `width_bucket(v, lo, hi, n)` | Histogram bucket | — |

Aggregates: `sum`, `avg`, `min`, `max`, `count`, `stddev`, `variance`.

```sql
SELECT sum(price), avg(price), round(avg(price), 2) FROM prices;
SELECT n, n * n AS square FROM generate_series(1, 5) AS n;
```

### 1.7 Casting and Rounding

```sql
SELECT CAST('42' AS integer);
SELECT '42'::integer;
SELECT 3.7::integer;                 -- 4 (rounds, does not truncate)
SELECT 7::numeric / 2;               -- 3.5000000000000000
SELECT 7 / 2.0;                      -- 3.5000000000000000
```

**Rounding behavior differs by type:**

```sql
SELECT round(2.5::numeric);    -- 3  (half away from zero)
SELECT round(2.5::float8);     -- 2  (round-half-even on most platforms)
```

Format numbers for display with `to_char`:

```sql
SELECT to_char(1234567.891, 'FM9,999,999.00');   -- 1,234,567.89
```

### 1.8 Common Pitfalls

| Pitfall | Fix |
|---|---|
| `7 / 2` returns `3` | Cast one operand: `7 / 2.0` or `7::numeric / 2` |
| Money calculations drift | Use `numeric(p,s)`, not `float` |
| `integer` overflow on IDs | Use `bigint` for large tables |
| Sequence gaps after rollback | Expected. Do not depend on contiguous IDs |
| `NULL` in arithmetic | `5 + NULL` is `NULL`. Use `coalesce(x, 0)` |
| `avg` of integers | Returns `numeric`, not integer |
| Division by zero | Raises error. Use `nullif(divisor, 0)` |

```sql
SELECT total / nullif(count, 0) FROM stats;
```

## 2. JSON and JSONB

### 2.1 json vs jsonb

PostgreSQL has two JSON types.

| Feature | `json` | `jsonb` |
|---|---|---|
| Storage | Exact copy of input text | Decomposed binary format |
| Whitespace and key order | Preserved | Not preserved |
| Duplicate keys | Kept (all stored) | Last value wins |
| Insert speed | Faster | Slightly slower (parsing) |
| Query speed | Slower (re-parsed each time) | **Faster** |
| Indexing | Not directly | **GIN, B-tree, hash** |
| Containment (`@>`) and existence (`?`) operators | No | **Yes** |

> **Default choice: `jsonb`.** Use `json` only when you must preserve the exact original text (e.g. audit logs, key ordering).

```sql
SELECT '{"b": 2, "a": 1, "a": 3}'::json;    -- {"b": 2, "a": 1, "a": 3}
SELECT '{"b": 2, "a": 1, "a": 3}'::jsonb;   -- {"a": 3, "b": 2}
```

### 2.2 Creating JSON Data

```sql
CREATE TABLE events (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload jsonb NOT NULL
);

INSERT INTO events (payload) VALUES
('{"type": "login",  "user": {"id": 1, "name": "Alice"}, "tags": ["web", "mobile"]}'),
('{"type": "purchase", "user": {"id": 2, "name": "Bob"},  "amount": 49.99, "tags": ["web"]}'),
('{"type": "logout", "user": {"id": 1, "name": "Alice"}}');
```

**Building JSON from SQL values**

```sql
SELECT jsonb_build_object('id', 1, 'name', 'Alice');
-- {"id": 1, "name": "Alice"}

SELECT jsonb_build_array(1, 'two', 3.0, null);
-- [1, "two", 3.0, null]

SELECT to_jsonb(c) FROM customers c LIMIT 1;    -- a whole row as JSON

SELECT jsonb_agg(to_jsonb(c)) FROM customers c; -- rows to a JSON array
```

The JSON value types are: object, array, string, number, boolean, and null. Note that JSON `null` is different from SQL `NULL`.

### 2.3 Accessing Data

| Operator | Returns | Description |
|---|---|---|
| `->` | `jsonb` | Get object field by key, or array element by index |
| `->>` | `text` | Same, but returns text |
| `#>` | `jsonb` | Get value at a path (text array) |
| `#>>` | `text` | Get value at a path as text |

```sql
SELECT payload -> 'type'              FROM events;  -- "login"  (jsonb)
SELECT payload ->> 'type'             FROM events;  -- login    (text)
SELECT payload -> 'user' ->> 'name'   FROM events;  -- Alice
SELECT payload #>> '{user,name}'      FROM events;  -- Alice
SELECT payload -> 'tags' -> 0         FROM events;  -- "web"
SELECT payload ->> 'amount'           FROM events;  -- '49.99' (text)
SELECT (payload ->> 'amount')::numeric FROM events; -- cast for math
```

**Subscripting (PostgreSQL 14+)**

```sql
SELECT payload['user']['name'] FROM events;      -- "Alice" (jsonb)
UPDATE events SET payload['status'] = '"done"' WHERE id = 1;
```

Missing keys return SQL `NULL` (no error).

**Filtering**

```sql
SELECT * FROM events WHERE payload ->> 'type' = 'purchase';
SELECT * FROM events WHERE (payload ->> 'amount')::numeric > 20;
```

### 2.4 Containment and Existence Operators

`jsonb` only.

| Operator | Description | Example |
|---|---|---|
| `@>` | Left contains right | `payload @> '{"type":"login"}'` |
| `<@` | Left is contained in right | `'{"a":1}' <@ payload` |
| `?` | Key or array element exists (top level) | `payload ? 'amount'` |
| `?\|` | Any of the keys exist | `payload ?\| array['amount','tags']` |
| `?&` | All of the keys exist | `payload ?& array['type','user']` |
| `@?` | jsonpath returns any item | `payload @? '$.user.id'` |
| `@@` | jsonpath predicate is true | `payload @@ '$.amount > 40'` |

```sql
SELECT * FROM events WHERE payload @> '{"user": {"id": 1}}';
SELECT * FROM events WHERE payload -> 'tags' ? 'mobile';
```

> Containment (`@>`) works with nested structures and is what GIN indexes accelerate best.

### 2.5 Modifying jsonb

| Operator / Function | Description |
|---|---|
| `a \|\| b` | Concatenate / merge objects (right side wins on conflicts) |
| `a - 'key'` | Delete a key |
| `a - 2` | Delete an array element by index |
| `a #- '{path}'` | Delete at a path |
| `jsonb_set(target, path, new_value, create_missing)` | Replace or add a value at a path |
| `jsonb_insert(target, path, new_value, after)` | Insert into an array or object |
| `jsonb_strip_nulls(x)` | Remove keys with JSON null values |

```sql
-- Merge
UPDATE events SET payload = payload || '{"processed": true}' WHERE id = 1;

-- Set a nested value
UPDATE events
SET payload = jsonb_set(payload, '{user,name}', '"Alicia"')
WHERE id = 1;

-- Add to an array (append)
UPDATE events
SET payload = jsonb_set(payload, '{tags}', (payload -> 'tags') || '"beta"')
WHERE id = 1;

-- Remove a key
UPDATE events SET payload = payload - 'processed' WHERE id = 1;

-- Remove a nested key
UPDATE events SET payload = payload #- '{user,name}' WHERE id = 1;
```

Notes:

- The new value passed to `jsonb_set` must be valid `jsonb` (strings need double quotes inside single quotes: `'"text"'`).
- `jsonb_set(...)` returns SQL `NULL` if the new value is SQL `NULL`. Use `to_jsonb()` or `coalesce`.
- Updating any part of a large jsonb value rewrites the **whole** value. Very large, frequently updated documents can be costly.

### 2.6 Expanding and Aggregating

**Set-returning functions**

| Function | Output |
|---|---|
| `jsonb_each(obj)` | Key/value pairs (`jsonb` values) |
| `jsonb_each_text(obj)` | Key/value pairs (text values) |
| `jsonb_object_keys(obj)` | Set of keys |
| `jsonb_array_elements(arr)` | One row per array element (`jsonb`) |
| `jsonb_array_elements_text(arr)` | One row per element (text) |
| `jsonb_array_length(arr)` | Length |
| `jsonb_typeof(x)` | `object`, `array`, `string`, `number`, `boolean`, `null` |
| `jsonb_populate_record(base, obj)` | Convert to a row of a known type |
| `jsonb_to_record(obj) AS t(col type, ...)` | Convert to columns |
| `jsonb_pretty(x)` | Indented output |

```sql
-- One row per tag
SELECT e.id, t.tag
FROM events e,
     jsonb_array_elements_text(e.payload -> 'tags') AS t(tag);

-- Object to key/value rows
SELECT key, value FROM events, jsonb_each_text(payload) WHERE id = 1;

-- Convert to typed columns
SELECT * FROM events,
     jsonb_to_record(payload) AS x(type text, amount numeric)
WHERE x.amount IS NOT NULL;
```

**Aggregation**

```sql
SELECT payload ->> 'type' AS type, count(*)
FROM events GROUP BY 1;

SELECT jsonb_agg(payload -> 'user' ->> 'name') FROM events;
SELECT jsonb_object_agg(id, payload ->> 'type') FROM events;
```

### 2.7 jsonpath

`jsonpath` (PostgreSQL 12+) is a query language for JSON, similar to XPath.

```sql
SELECT jsonb_path_query(payload, '$.user.name') FROM events;
SELECT jsonb_path_query(payload, '$.tags[*]') FROM events;          -- each element
SELECT jsonb_path_exists(payload, '$.amount ? (@ > 40)') FROM events;
SELECT * FROM events WHERE payload @@ '$.amount > 40';
SELECT jsonb_path_query_array(payload, '$.tags[*]') FROM events;
```

Path syntax essentials: `$` is the root, `.key` selects a field, `[n]` and `[*]` select array elements, `? (...)` filters, and `@` refers to the current item.

### 2.8 Indexing jsonb

**GIN index** (best for `@>`, `?`, `?|`, `?&`, and jsonpath operators)

```sql
-- Default operator class: supports @>, ?, ?|, ?&, @?, @@
CREATE INDEX idx_events_payload ON events USING gin (payload);

-- jsonb_path_ops: smaller and faster, but supports only @>, @?, @@
CREATE INDEX idx_events_payload_path ON events USING gin (payload jsonb_path_ops);
```

**B-tree expression index** (for equality or range on one extracted key)

```sql
CREATE INDEX idx_events_type ON events ((payload ->> 'type'));

-- Queries must use the same expression:
SELECT * FROM events WHERE payload ->> 'type' = 'login';
```

**Partial and typed expression indexes**

```sql
CREATE INDEX idx_purchases_amount
ON events (((payload ->> 'amount')::numeric))
WHERE payload ->> 'type' = 'purchase';
```

| Index | Good for | Notes |
|---|---|---|
| GIN (default) | Many different queries on arbitrary keys | Larger, slower writes |
| GIN `jsonb_path_ops` | Containment lookups | Smaller, faster; fewer operators |
| B-tree expression | Frequently filtered or sorted single key | Query must match the expression exactly |

### 2.9 SQL/JSON Features in Newer Versions

| Version | Additions |
|---|---|
| 12 | `jsonpath` and the `jsonb_path_*` functions |
| 14 | `jsonb` subscripting (`col['key']`) |
| 16 | SQL/JSON constructors (`JSON_ARRAY`, `JSON_OBJECT`, ...), `IS JSON` predicates |
| 17 | `JSON_EXISTS`, `JSON_QUERY`, `JSON_VALUE`, and `JSON_TABLE` (turn JSON into relational rows) |

```sql
-- PostgreSQL 16+
SELECT '{"a":1}' IS JSON OBJECT;                -- true

-- PostgreSQL 17+
SELECT JSON_VALUE(payload, '$.user.name') FROM events;
```

### 2.10 When to Use JSON vs Relational Columns

**Good fits for jsonb:**

- Semi-structured or variable attributes (product specs, user preferences)
- Storing third-party API payloads or event logs
- Rapid prototyping where the schema is unsettled

**Prefer regular columns when:**

- Fields are always present and frequently filtered or joined
- You need foreign keys, strong typing, and `NOT NULL` or `CHECK` guarantees on those fields
- Values are updated often (whole-document rewrite cost)

A common hybrid: relational columns for core fields plus one `jsonb` column for the flexible remainder.

## 3. hstore

### 3.1 What Is hstore?

`hstore` is an extension that adds a data type for storing **flat sets of key/value pairs**, where both keys and values are **text** (values may also be `NULL`). It predates `jsonb` and is simpler, with no nesting and no arrays.

### 3.2 Enabling and Creating Values

```sql
CREATE EXTENSION IF NOT EXISTS hstore;
\dx hstore

CREATE TABLE products (
    id    serial PRIMARY KEY,
    name  text,
    attrs hstore
);

INSERT INTO products (name, attrs) VALUES
('T-shirt', 'color => red, size => M, material => cotton'),
('Laptop',  'brand => "Acme", ram => "16GB", ssd => "512GB"'),
('Mug',     'color => white, note => NULL');
```

Literal rules: pairs are separated by commas, key and value by `=>`, and double quotes are needed if a key or value contains spaces, commas, or `=>`.

```sql
SELECT hstore('a', 'b');                              -- "a"=>"b"
SELECT hstore(ARRAY['k1','k2'], ARRAY['v1','v2']);    -- "k1"=>"v1", "k2"=>"v2"
SELECT hstore(ROW(1, 'x'));                           -- from a row
```

### 3.3 Operators

| Operator | Description | Example |
|---|---|---|
| `->` | Get value by key (text) | `attrs -> 'color'` |
| `-> text[]` | Get values for several keys (array) | `attrs -> ARRAY['color','size']` |
| `\|\|` | Concatenate (right side wins) | `attrs \|\| 'size=>L'` |
| `?` | Key exists | `attrs ? 'color'` |
| `?&` | All keys exist | `attrs ?& ARRAY['color','size']` |
| `?\|` | Any key exists | `attrs ?\| ARRAY['color','brand']` |
| `@>` | Left contains right | `attrs @> 'color=>red'` |
| `<@` | Left is contained in right | `'color=>red' <@ attrs` |
| `- text` | Delete a key | `attrs - 'note'` |
| `- text[]` | Delete several keys | `attrs - ARRAY['a','b']` |
| `- hstore` | Delete matching pairs | `attrs - 'color=>red'` |
| `%%` / `%#` | Convert to array / 2-D array | `%% attrs` |

```sql
SELECT name, attrs -> 'color' AS color FROM products;
SELECT name FROM products WHERE attrs ? 'ram';
SELECT name FROM products WHERE attrs @> 'color=>red';
SELECT name FROM products WHERE (attrs -> 'size') = 'M';
```

PostgreSQL 14+ also supports subscripting: `attrs['color']`.

### 3.4 Functions

| Function | Description | Example result |
|---|---|---|
| `akeys(h)` / `skeys(h)` | Keys as array / set | `{color,size}` |
| `avals(h)` / `svals(h)` | Values as array / set | `{red,M}` |
| `each(h)` | Rows of `(key, value)` | — |
| `exist(h, k)` | Same as `?` | `t` |
| `defined(h, k)` | Key exists **and** value is not NULL | `f` for `note` |
| `delete(h, k)` | Remove key | — |
| `slice(h, keys[])` | Sub-hstore with selected keys | — |
| `hstore_to_array(h)` | Flat array `{k1,v1,k2,v2}` | — |
| `hstore_to_matrix(h)` | 2-D array | — |
| `hstore_to_json(h)` / `hstore_to_jsonb(h)` | Convert to JSON | `{"color": "red"}` |
| `populate_record(base, h)` | Fill a row type from hstore | — |

```sql
SELECT skeys(attrs) FROM products WHERE name = 'T-shirt';
SELECT * FROM each((SELECT attrs FROM products WHERE name = 'Laptop'));
SELECT hstore_to_jsonb(attrs) FROM products;
SELECT DISTINCT k FROM products, skeys(attrs) AS k ORDER BY k;   -- catalog of all keys
```

### 3.5 Updating hstore Columns

```sql
-- Add or change a key
UPDATE products SET attrs = attrs || 'weight => 200g' WHERE name = 'Mug';

-- Change several
UPDATE products SET attrs = attrs || hstore(ARRAY['color','size'], ARRAY['blue','L'])
WHERE name = 'T-shirt';

-- Remove a key
UPDATE products SET attrs = delete(attrs, 'note') WHERE name = 'Mug';
UPDATE products SET attrs = attrs - 'note' WHERE name = 'Mug';
```

### 3.6 Indexing hstore

| Index type | Supports | Notes |
|---|---|---|
| **GIN** | `@>`, `?`, `?&`, `?\|` | Fast lookups, slower updates |
| **GiST** | `@>`, `?`, `?&`, `?\|` | Lossy, smaller, faster updates, slower lookups |
| **B-tree / Hash** | `=` on the whole hstore | Rarely useful |
| **Expression B-tree** | `attrs -> 'key'` | Best for one hot key |

```sql
CREATE INDEX idx_products_attrs ON products USING gin (attrs);
CREATE INDEX idx_products_color ON products ((attrs -> 'color'));
```

### 3.7 hstore vs jsonb

| Aspect | hstore | jsonb |
|---|---|---|
| Nesting | No (flat only) | Yes |
| Value types | Text only (and NULL) | string, number, boolean, null, object, array |
| Standard | PostgreSQL-specific extension | Standard JSON, widely supported |
| Installation | `CREATE EXTENSION` needed | Built in |
| Tooling and drivers | Limited | Excellent |
| Performance | Very good for flat text maps | Very good; richer features |

**Guidance:** For new work, prefer `jsonb`. Use hstore when data is a truly flat string map and you want simpler operators, or when maintaining existing systems.

## 4. Constraints

### 4.1 Overview

Constraints enforce data integrity rules **inside the database**, regardless of which application writes the data.

| Constraint | Purpose |
|---|---|
| `NOT NULL` | Column cannot hold `NULL` |
| `UNIQUE` | Values (or combinations) must be unique |
| `PRIMARY KEY` | Unique + not null; identifies each row |
| `FOREIGN KEY` | Value must exist in another table's key |
| `CHECK` | Arbitrary boolean condition on the row |
| `EXCLUDE` | No two rows may conflict under given operators (generalized uniqueness) |

`DEFAULT` supplies a value when none is given. It is not formally a constraint but is defined alongside them.

**Column vs table constraints**

```sql
CREATE TABLE employees (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    email      text    NOT NULL,                 -- column constraint
    salary     numeric(10,2) CHECK (salary > 0), -- column constraint
    dept_id    integer,
    CONSTRAINT pk_employees PRIMARY KEY (id),    -- table constraints
    CONSTRAINT uq_employees_email UNIQUE (email)
);
```

> **Always name your constraints** (`CONSTRAINT name ...`). Error messages and later `ALTER`/`DROP` operations become far clearer.

### 4.2 NOT NULL and DEFAULT

```sql
CREATE TABLE tasks (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title      text        NOT NULL,
    status     text        NOT NULL DEFAULT 'open',
    created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO tasks (title) VALUES ('Write docs');
INSERT INTO tasks (title) VALUES (NULL);            -- ERROR: null value violates not-null constraint

ALTER TABLE tasks ALTER COLUMN title SET NOT NULL;
ALTER TABLE tasks ALTER COLUMN title DROP NOT NULL;
ALTER TABLE tasks ALTER COLUMN status SET DEFAULT 'new';
ALTER TABLE tasks ALTER COLUMN status DROP DEFAULT;
```

- Adding `NOT NULL` to an existing column scans the table to verify no nulls exist.
- Since PostgreSQL 11, adding a column with a constant `DEFAULT` is fast (no full rewrite).
- Use `DEFAULT` to fill in explicitly: `INSERT INTO tasks (title, status) VALUES ('x', DEFAULT);`

### 4.3 UNIQUE

```sql
CREATE TABLE users (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username text,
    email    text,
    CONSTRAINT uq_users_username UNIQUE (username),
    CONSTRAINT uq_users_org_email UNIQUE (org_id, email)   -- composite (assumes org_id column)
);
```

- Backed by an automatically created **unique B-tree index**.
- **NULLs are distinct by default.** Multiple rows with `NULL` in a unique column are allowed.
- PostgreSQL 15+: `UNIQUE NULLS NOT DISTINCT` treats NULLs as equal, allowing only one NULL.

```sql
ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE NULLS NOT DISTINCT (email);
```

**Case-insensitive uniqueness** (use a unique index on an expression):

```sql
CREATE UNIQUE INDEX uq_users_lower_email ON users (lower(email));
```

**Partial uniqueness:**

```sql
CREATE UNIQUE INDEX uq_active_username ON users (username) WHERE deleted_at IS NULL;
```

### 4.4 PRIMARY KEY

```sql
CREATE TABLE departments (
    id   integer PRIMARY KEY,
    name text NOT NULL
);

-- Composite primary key
CREATE TABLE order_items (
    order_id   bigint,
    product_id bigint,
    qty        integer NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
```

- Implies `UNIQUE` and `NOT NULL`, and creates an index.
- **Only one** primary key per table (but any number of `UNIQUE` constraints).
- Choose stable, meaningful-free surrogate keys (identity or UUID) unless a natural key is truly immutable.

### 4.5 FOREIGN KEY

```sql
CREATE TABLE employees (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name    text NOT NULL,
    dept_id integer,
    CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id)
        REFERENCES departments (id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

-- Shorthand for a single column
-- dept_id integer REFERENCES departments (id)
```

**Referential actions** (what happens when the referenced row is deleted or updated):

| Action | Behavior |
|---|---|
| `NO ACTION` (default) | Error if referencing rows exist; check can be deferred to end of statement/transaction |
| `RESTRICT` | Error immediately; cannot be deferred |
| `CASCADE` | Delete or update the referencing rows too |
| `SET NULL` | Set referencing column(s) to `NULL` |
| `SET DEFAULT` | Set referencing column(s) to their default |

PostgreSQL 15+ allows `ON DELETE SET NULL (column_list)` to null only specific columns of a composite key.

**MATCH options** (for composite keys): `MATCH SIMPLE` (default: any NULL column skips the check) and `MATCH FULL` (all columns must be NULL or none).

**Important details**

- The referenced columns must have a `UNIQUE` or `PRIMARY KEY` constraint.
- PostgreSQL does **not** automatically index the referencing (child) column. Add an index manually. It makes deletes and updates on the parent table much faster.

```sql
CREATE INDEX idx_employees_dept_id ON employees (dept_id);
```

- A `NULL` foreign key value is allowed unless the column is `NOT NULL`.
- Self-referencing keys are allowed: `manager_id bigint REFERENCES employees (id)`.

### 4.6 CHECK

```sql
CREATE TABLE products (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name     text NOT NULL,
    price    numeric(10,2) NOT NULL CONSTRAINT ck_price_positive CHECK (price >= 0),
    discount numeric(4,2),
    status   text,
    CONSTRAINT ck_status CHECK (status IN ('draft', 'active', 'retired')),
    CONSTRAINT ck_discount CHECK (discount IS NULL OR discount BETWEEN 0 AND 0.90),
    CONSTRAINT ck_price_vs_discount CHECK (discount IS NULL OR price * (1 - discount) > 0)
);
```

- A row passes if the condition evaluates to **TRUE or NULL**. Only `FALSE` rejects it. Combine with `NOT NULL` when needed.
- Conditions can reference multiple columns of the **same row**.
- CHECK expressions cannot contain subqueries and should be immutable.
- Reusable rules can be defined with **domains**:

```sql
CREATE DOMAIN positive_int AS integer CHECK (VALUE > 0);
CREATE TABLE items (qty positive_int);
```

### 4.7 EXCLUDE

Exclusion constraints generalize uniqueness: "no two rows may satisfy these operators against each other." A classic use is preventing overlapping bookings.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_bookings (
    room_id int,
    during  tstzrange,
    EXCLUDE USING gist (
        room_id WITH =,
        during  WITH &&
    )
);

INSERT INTO room_bookings VALUES (1, '[2026-03-01 09:00, 2026-03-01 11:00)');
INSERT INTO room_bookings VALUES (1, '[2026-03-01 10:00, 2026-03-01 12:00)');
-- ERROR: conflicting key value violates exclusion constraint
```

### 4.8 Generated Columns

Not a constraint, but often taught alongside them: a column whose value is computed from other columns and stored on disk.

```sql
CREATE TABLE rectangles (
    w    numeric NOT NULL,
    h    numeric NOT NULL,
    area numeric GENERATED ALWAYS AS (w * h) STORED
);
```

- The expression must be immutable and can use only the same row's columns.
- Cannot be written directly.
- PostgreSQL 18 adds virtual generated columns (computed at read time). Check your version.

### 4.9 Managing Constraints

```sql
-- Add
ALTER TABLE employees ADD CONSTRAINT ck_salary CHECK (salary > 0);
ALTER TABLE employees ADD CONSTRAINT uq_emp_email UNIQUE (email);
ALTER TABLE employees ADD CONSTRAINT fk_emp_dept
    FOREIGN KEY (dept_id) REFERENCES departments (id);

-- Drop
ALTER TABLE employees DROP CONSTRAINT ck_salary;
ALTER TABLE employees DROP CONSTRAINT IF EXISTS uq_emp_email;

-- Rename
ALTER TABLE employees RENAME CONSTRAINT fk_emp_dept TO fk_employees_department;
```

**Adding constraints to large, busy tables safely**

`ADD CONSTRAINT` normally scans the whole table while holding a strong lock. Split the work:

```sql
-- Step 1: quick, only affects new/changed rows
ALTER TABLE employees
    ADD CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id)
    REFERENCES departments (id) NOT VALID;

-- Step 2: validate existing rows with a weaker lock
ALTER TABLE employees VALIDATE CONSTRAINT fk_emp_dept;
```

`NOT VALID` works for `CHECK` and `FOREIGN KEY` constraints.

For unique constraints on big tables, build the index first, then attach it:

```sql
CREATE UNIQUE INDEX CONCURRENTLY uq_emp_email_idx ON employees (email);
ALTER TABLE employees ADD CONSTRAINT uq_emp_email UNIQUE USING INDEX uq_emp_email_idx;
```

### 4.10 Deferrable Constraints

By default, constraints are checked at the end of each **statement**. Deferrable constraints can be checked at **commit**.

```sql
CREATE TABLE nodes (
    id        integer PRIMARY KEY,
    parent_id integer,
    CONSTRAINT fk_parent FOREIGN KEY (parent_id) REFERENCES nodes (id)
        DEFERRABLE INITIALLY IMMEDIATE
);

BEGIN;
SET CONSTRAINTS fk_parent DEFERRED;
INSERT INTO nodes VALUES (2, 1);   -- parent 1 doesn't exist yet: allowed for now
INSERT INTO nodes VALUES (1, NULL);
COMMIT;                            -- checked here: OK
```

- Applies to `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, and `EXCLUDE`. It does not apply to `CHECK` or `NOT NULL`.
- Useful for swapping unique values between rows or loading circular references.

### 4.11 Inspecting Constraints

```
\d employees          -- shows constraints, indexes, and referencing tables
\d+ employees
```

```sql
SELECT conname, contype, pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid = 'employees'::regclass;
-- contype: p = primary, u = unique, f = foreign, c = check, x = exclusion

SELECT constraint_name, constraint_type
FROM information_schema.table_constraints
WHERE table_name = 'employees';
```

## 5. DML: Data Manipulation Language

DML statements read and change table data: `INSERT`, `UPDATE`, `DELETE`, `MERGE` (and `SELECT` for reading). `TRUNCATE` and `COPY` are related bulk operations.

Sample tables used below:

```sql
CREATE TABLE accounts (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    owner   text NOT NULL,
    balance numeric(12,2) NOT NULL DEFAULT 0 CHECK (balance >= 0),
    email   text UNIQUE
);
```

### 5.1 INSERT

```sql
-- Single row, explicit columns (always list columns)
INSERT INTO accounts (owner, balance, email)
VALUES ('Alice', 100.00, 'alice@example.com');

-- Multiple rows in one statement (faster than many single inserts)
INSERT INTO accounts (owner, balance, email) VALUES
    ('Bob',   250.00, 'bob@example.com'),
    ('Carol',  75.50, 'carol@example.com');

-- Use defaults
INSERT INTO accounts (owner) VALUES ('Dave');            -- balance = 0
INSERT INTO accounts (owner, balance) VALUES ('Eve', DEFAULT);
INSERT INTO accounts DEFAULT VALUES;                     -- fails here: owner NOT NULL

-- From a query
INSERT INTO accounts_archive (id, owner, balance)
SELECT id, owner, balance FROM accounts WHERE balance = 0;

-- Generated test data
INSERT INTO accounts (owner, balance)
SELECT 'user_' || g, (random() * 1000)::numeric(12,2)
FROM generate_series(1, 1000) AS g;
```

Tips:

- Omitted columns receive their `DEFAULT` (or `NULL`).
- Constraint violations abort the **entire** statement. No partial inserts.
- For very large loads, prefer `COPY` (see 5.8).

### 5.2 UPDATE

```sql
-- Basic
UPDATE accounts SET balance = balance + 50 WHERE owner = 'Alice';

-- Multiple columns
UPDATE accounts
SET balance = 0, email = NULL
WHERE owner = 'Dave';

-- Tuple assignment
UPDATE accounts SET (owner, email) = ('Alice B.', 'alice.b@example.com') WHERE id = 1;

-- Using data from another table (UPDATE ... FROM)
UPDATE accounts a
SET balance = a.balance + b.bonus
FROM bonuses b
WHERE a.id = b.account_id;

-- Using a subquery
UPDATE accounts
SET balance = balance * 1.02
WHERE id IN (SELECT account_id FROM premium_members);
```

> **Always double-check your `WHERE` clause.** `UPDATE accounts SET balance = 0;` updates **every row**. In psql, wrap risky statements in a transaction so you can `ROLLBACK`.

**MVCC note:** An `UPDATE` writes a new row version. Heavy updates create dead tuples that `VACUUM` must reclaim.

### 5.3 DELETE

```sql
DELETE FROM accounts WHERE balance = 0;

-- Using another table
DELETE FROM accounts a
USING closed_accounts c
WHERE a.id = c.account_id;

-- With a subquery
DELETE FROM accounts
WHERE id IN (SELECT account_id FROM fraud_flags);

-- Delete everything (slow for big tables; see TRUNCATE)
DELETE FROM accounts;
```

- Foreign key actions (`CASCADE`, `SET NULL`, ...) fire during deletes.
- Deleted rows are marked dead and reclaimed later by vacuum. Disk space is not immediately returned to the OS.

### 5.4 RETURNING

`INSERT`, `UPDATE`, `DELETE` (and `MERGE` in PostgreSQL 17+) can return the affected rows, avoiding an extra `SELECT`.

```sql
-- Get generated IDs
INSERT INTO accounts (owner, balance) VALUES ('Frank', 10)
RETURNING id, owner;

-- See old vs new state after an update
UPDATE accounts SET balance = balance - 20 WHERE id = 1
RETURNING id, balance;

-- Capture what was deleted
DELETE FROM accounts WHERE balance = 0
RETURNING *;
```

PostgreSQL 18 also lets `RETURNING` reference both `OLD` and `NEW` values.

### 5.5 Upsert: INSERT ON CONFLICT

"Insert if new, otherwise do something else." Requires a unique index or constraint to detect the conflict.

```sql
-- Ignore duplicates
INSERT INTO accounts (owner, balance, email)
VALUES ('Alice', 100, 'alice@example.com')
ON CONFLICT (email) DO NOTHING;

-- Update on duplicate
INSERT INTO accounts (owner, balance, email)
VALUES ('Alice', 100, 'alice@example.com')
ON CONFLICT (email)
DO UPDATE SET balance = accounts.balance + EXCLUDED.balance;

-- Conditional update
INSERT INTO accounts (owner, balance, email)
VALUES ('Alice', 500, 'alice@example.com')
ON CONFLICT (email)
DO UPDATE SET balance = EXCLUDED.balance
WHERE accounts.balance < EXCLUDED.balance
RETURNING *;

-- Conflict on a named constraint
ON CONFLICT ON CONSTRAINT accounts_email_key DO NOTHING
```

- `EXCLUDED` refers to the row that **would have been inserted**.
- The unqualified table name (or alias) refers to the **existing** row.
- `ON CONFLICT` is atomic and safe under concurrency, unlike a manual "select, then insert or update" in application code.
- With `DO NOTHING`, `RETURNING` returns only rows actually inserted.
- One statement cannot update the same row twice: "ON CONFLICT DO UPDATE command cannot affect row a second time".

### 5.6 MERGE

`MERGE` (PostgreSQL 15+) combines insert, update and delete in one statement driven by a join between a target and a source.

```sql
MERGE INTO inventory AS t
USING incoming_stock AS s
ON t.sku = s.sku
WHEN MATCHED AND s.qty = 0 THEN
    DELETE
WHEN MATCHED THEN
    UPDATE SET qty = t.qty + s.qty, updated_at = now()
WHEN NOT MATCHED THEN
    INSERT (sku, qty, updated_at) VALUES (s.sku, s.qty, now());
```

| Clause | Version | Meaning |
|---|---|---|
| `WHEN MATCHED` | 15+ | Source row matches a target row |
| `WHEN NOT MATCHED` (`BY TARGET`) | 15+ | Source row has no matching target row |
| `WHEN NOT MATCHED BY SOURCE` | 17+ | Target row has no matching source row |
| `RETURNING` (with `merge_action()`) | 17+ | Return affected rows and which action ran |

**MERGE vs ON CONFLICT:** `ON CONFLICT` is the simpler, concurrency-hardened choice for single-table upserts on a unique key. `MERGE` is more flexible (arbitrary join conditions, deletes, several actions) but can raise unique violations under concurrent inserts.

### 5.7 TRUNCATE

Quickly removes **all rows** from one or more tables by discarding storage.

```sql
TRUNCATE TABLE accounts;
TRUNCATE accounts, transactions;
TRUNCATE accounts RESTART IDENTITY;      -- reset identity/sequence counters
TRUNCATE accounts CASCADE;               -- also truncate tables with FKs pointing here
```

| | `DELETE` | `TRUNCATE` |
|---|---|---|
| Removes | Rows matching `WHERE` | All rows |
| Speed on big tables | Slow | Very fast |
| Space reclaimed | After vacuum | Immediately |
| Row-level triggers | Fire | Do not fire (statement-level `TRUNCATE` triggers do) |
| Transaction-safe | Yes | **Yes** (unlike in some other databases) |
| Lock | Row locks | `ACCESS EXCLUSIVE` on the table |

### 5.8 COPY

Fast bulk load and export.

```sql
-- Server-side (file on the DB server; needs privileges)
COPY accounts (owner, balance, email)
FROM '/var/lib/postgresql/import/accounts.csv'
WITH (FORMAT csv, HEADER true);

COPY (SELECT * FROM accounts WHERE balance > 100)
TO '/tmp/rich.csv' WITH (FORMAT csv, HEADER true);
```

Client-side from psql (file on **your** machine):

```
\copy accounts (owner, balance, email) FROM 'accounts.csv' WITH (FORMAT csv, HEADER true)
\copy (SELECT * FROM accounts) TO 'accounts_out.csv' WITH (FORMAT csv, HEADER true)
```

`COPY` is typically many times faster than individual `INSERT`s. Constraints and triggers still apply.

### 5.9 Data-Modifying CTEs

`WITH` queries can contain `INSERT`, `UPDATE`, or `DELETE ... RETURNING`, enabling multi-step operations in one statement.

```sql
-- Move rows from one table to another atomically
WITH moved AS (
    DELETE FROM accounts
    WHERE balance = 0
    RETURNING *
)
INSERT INTO accounts_archive (id, owner, balance, email)
SELECT id, owner, balance, email FROM moved;

-- Insert a parent and children together
WITH new_order AS (
    INSERT INTO orders (customer_id) VALUES (42) RETURNING id
)
INSERT INTO order_items (order_id, product_id, qty)
SELECT id, 7, 3 FROM new_order;
```

All sub-statements see the **same snapshot**, and the whole statement succeeds or fails as one unit.

### 5.10 Transactions and DML

Every statement runs in a transaction. Group related DML explicitly for atomicity.

```sql
BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE owner = 'Alice';
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Bob';

-- Verify, then:
COMMIT;      -- or ROLLBACK;
```

**Savepoints** allow partial rollback:

```sql
BEGIN;
INSERT INTO accounts (owner) VALUES ('Grace');
SAVEPOINT sp1;
INSERT INTO accounts (owner) VALUES (NULL);     -- fails
ROLLBACK TO SAVEPOINT sp1;                      -- transaction usable again
COMMIT;                                         -- Grace is saved
```

- After an error inside a transaction block, the transaction is **aborted**. Only `ROLLBACK` (or `ROLLBACK TO SAVEPOINT`) is accepted.
- `psql` runs in autocommit mode by default: each statement commits immediately.

**Locking rows for update**

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;      -- lock the row
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
COMMIT;

-- Job-queue pattern: skip rows locked by other workers
SELECT * FROM jobs WHERE status = 'queued'
ORDER BY id LIMIT 1
FOR UPDATE SKIP LOCKED;
```

## 7. Quick Reference Cheat Sheet

**Numeric**

| Need | Use |
|---|---|
| IDs, counts | `integer` / `bigint` (`GENERATED ... AS IDENTITY`) |
| Money, exact decimals | `numeric(p,s)` |
| Scientific data | `double precision` |
| Avoid integer division | `7 / 2.0` or `7::numeric / 2` |
| Avoid divide-by-zero | `x / nullif(y, 0)` |

**JSONB**

```sql
col -> 'k'   col ->> 'k'   col #>> '{a,b}'   col['a']['b']     -- access
col @> '{"k":"v"}'   col ? 'k'   col @@ '$.n > 5'              -- search
col || '{"k":1}'   col - 'k'   jsonb_set(col,'{a,b}','1')      -- modify
jsonb_array_elements(col)   jsonb_each(col)   jsonb_agg(x)     -- expand / aggregate
CREATE INDEX ON t USING gin (col);                             -- index
```

**hstore**

```sql
CREATE EXTENSION hstore;
col -> 'k'   col ? 'k'   col @> 'k=>v'   col || 'k=>v'   col - 'k'
skeys(col)   svals(col)   each(col)   hstore_to_jsonb(col)
CREATE INDEX ON t USING gin (col);
```

**Constraints**

```sql
NOT NULL | DEFAULT x | UNIQUE (a,b) | PRIMARY KEY (a) |
FOREIGN KEY (a) REFERENCES p (id) ON DELETE CASCADE |
CHECK (x > 0) | EXCLUDE USING gist (...)
ALTER TABLE t ADD CONSTRAINT n ... NOT VALID;  ALTER TABLE t VALIDATE CONSTRAINT n;
```

**DML**

```sql
INSERT INTO t (a,b) VALUES (1,2), (3,4) RETURNING *;
INSERT ... ON CONFLICT (k) DO UPDATE SET c = EXCLUDED.c;
UPDATE t SET c = 1 FROM s WHERE t.id = s.id RETURNING *;
DELETE FROM t USING s WHERE t.id = s.id RETURNING *;
MERGE INTO t USING s ON t.id = s.id WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT ...;
TRUNCATE t RESTART IDENTITY;
BEGIN; ... SAVEPOINT x; ... ROLLBACK TO x; COMMIT;
```
